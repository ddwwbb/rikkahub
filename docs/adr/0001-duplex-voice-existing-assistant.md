# 双工语音沿用当前助手的 ASR → LLM → TTS 链路

用户已选择保留当前聊天模型、助手提示词、记忆、工具及审批，并让语音与文字共用 Conversation。因此双工语音沿用 ASR → 当前助手/LLM → TTS，通过处理后的增量回答片段进行播报，不另建专用原生语音模型会话；代价是首音延迟与声音自然度受三段链路和所选服务影响，不能承诺所有模型都达到原生语音体验。

## Consequences

- 收音和播报并行。人声触发停止播放并清空待播内容，有效最终转写到达后才取消旧生成、提交新话语；空转写不提交，也不自动恢复旧播报。
- 所有非空最终转写，包括短指令和附和词，都按顺序保留。新话语使旧回答轮次失效，下一次回答结合尚未回应的话语；迟到文本不接入新回答，迟到音频不播报。
- 保留已生成文字，并标记播报中断，使下一轮知道回答可能未被完整听到，不声称逐字掌握实际收听位置。
- 已开始的工具调用不因插话强行取消，其结果如实记录；新话语等待工具结果后再响应。待审批工具停止语音，审批仍在界面进行，处理后手动重启语音。
- 断句沿用所选 ASR 的服务端机制和现有配置，不提前提交临时转写。缺少所需 ASR 能力或可用 TTS 时，启动前明确阻止，不静默更换服务。
- 任一语音链路失败、退出前台或失去音频焦点时停止录音、合成和播放；已提交的聊天生成继续，但不再出声。切换会话、模型、助手、语音服务或发送文字时先结束语音；不自动重连、重试或重复提交。
- 前台耳机与手机外放属于验收范围，后台持续通话、嘈杂环境可靠性和非文字声音理解不属于硬要求。外放回声不可靠时明确提示并要求耳机，不静默降级，不将该外放组合计为通过。
- 每个声明支持的测试组合记录真机、模型、ASR/TTS 与网络条件，分别采集至少 100 次无工具问答与 100 次播报中插话，不删除慢样本。目标为用户实际说完至第一段有效回答 P95 ≤ 2 秒（包含断句等待），用户开始讲话至停止出声 P95 ≤ 500 ms；同时报告失败次数，验证不自答、不丢连续话语、不复活旧音频。

用户已授权实施。当前实现包括持续收音、插话轮次、可取消的流式音频播放和工具执行保护；性能数字仍是待实测的验收目标，不是已观测结果。具体外部服务和手机音频组合尚未完成验收，不能将本地回归通过声明为所有目标通过。

## 实施边界

- RikkaHub 新增 Voice Gateway ASR，连接 `ws://电脑IP:8080/v1/asr`，发送 `start.mode=voice`；普通输入仍用 dictation。OpenAIRealtime、DashScope 和直连火山也使用持续录音路径。火山与网关的本地 WebRTC GMM 活动仅辅助及时打断，最终句终与文字仍由上游确定。
- 独立 `VoiceTtsPlayer` 采用有界音频流、真实解码和可取消网络请求。任意输出正则或引号过滤可能改写先前正文，因此这类配置等待最终文字；其他正文按完整稳定片段增量播报。
- 耳机/外放资格以系统 AEC 和通信路由能力检查为基础，不声称能自动识别所有残余回声。实际音频路由改变后停止并要求重新开启，避免沿用旧路由的资格。
- 网关输入法协议的 VAD 起点、句终明细可能稀疏或迟到；缺失时不伪造 final，也不按未知时间戳切音频。累计最终文字完整保留，整体会话仍限 300 秒。
- 本地真实 HTTP/WS 对端、500 项相关 JVM 单测、Android 模拟器音频解码/播放/取消、真实录音 PCM 传输和界面片段已验证；网关 121 项协议测试及 fmt/clippy 通过。录音 fixture 只验证传输和文本保存，不证明上游识别准确率。随后移除 Firebase Analytics、Crashlytics 及其构建插件，完整 Debug APK 构建与 245 项 App JVM 单测通过；模拟器已正常进入聊天页，并通过长按发送保存用户消息，无需 `app/google-services.json`。该验证未覆盖真实模型回复和手机声学验收。
